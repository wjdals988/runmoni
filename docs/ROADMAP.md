# Runmoni 다음 개발 단계

기준: [2026-10-23 코드 감사](AUDIT_2026-10-23.md).
기존 5개 탭·개인 기록 우선 구조를 유지한다. 체크되지 않은 항목은 미완료다.
실기기와 클라우드 계정이 필요한 단계는 그 증거를 확보한 뒤에만 완료한다.

## 0. 재현 가능한 개발 기준선

- [x] 서버 입력 오버플로·날짜 경계·오디오 설정 계약 수정 및 회귀 테스트.
- [x] backend/bridge/SQL 구문/Android 빌드 GitHub Actions 설정 추가.
- [ ] 실제 Actions 전 job 통과 및 실패 시 report 수집 확인.
- [ ] 에뮬레이터 instrumentation을 별도 job 또는 수동 실행 절차로 재현.
- [ ] 브리지 전이 의존성 lock과 정기 의존성 점검. 버전 변경은 호환성 테스트를 동반.

완료 조건: 새 PC/CI에서 비밀 키 없이 서버·브리지 테스트와 Android debug/test APK를 만들 수 있고,
검증 문서가 실행한 커밋·환경·결과를 가리킨다.

## 1. 계정별 기록 소유권·동기화 복구 — 최우선 구현

대상: A01/A03/A04. 먼저 이 단계를 끝내고 외부 파일럿 인원을 늘린다.

- [ ] `StoredRun`에 로컬 보상과 서버 보상 분리, 서버 주소+안정적인 user ID에 연결되는 소유권 모델 설계.
- [ ] 계정별 sync 대상/업로드 상태/마지막 오류/재시도 시각을 별도 저장. 서버 변경을 전역 Boolean으로 표현하지 않기.
- [ ] 기존 Room v1 데이터 migration. 소유자를 알 수 없는 기존 기록은 임의 계정으로 자동 귀속하지 않기.
- [ ] 게스트 기록의 서버 업로드는 사용자가 대상 계정을 확인하는 동작으로 정의.
- [ ] 로그아웃/서버 변경 시 WorkManager·진행 중 API/presence 요청 정리. 이전 세션 응답은 폐기.
- [ ] 한 기록의 409/422가 다음 정상 기록을 막지 않도록 실패 격리. 401은 재인증 대기로 표시.
- [ ] 취소 예외를 retry로 삼키지 않고 전파. 재시도 UX와 서버/기기 상태 차이를 표시.

완료 조건: A/B 계정 교대, 서버 교체, 오프라인 종료, 업로드 중 종료, finalize 직후 응답 유실,
로그아웃 중 업로드, 한 기록 오류 뒤 정상 기록 업로드를 테스트한다.
다른 계정에 GPS가 자동 전송되지 않고 보상은 계정·기록별 1회만 지급되어야 한다.

## 2. 복구 가능한 인증과 계정 수명주기

대상: A02/A10. 기본 경로는 기존 SQL 방향과 맞는 Supabase Auth+PostgreSQL로 유지한다.
Firebase는 전환 결정을 별도로 내릴 때의 대안이다.

- [ ] 이메일 OTP 등 본인 확인 수단, 가입/재로그인/만료/다중 기기/복구 흐름.
- [ ] 파일럿 계정과 새 Auth ID를 연결하는 본인 확인·이관 정책. 닉네임이나 초대 코드만으로 계정 인수 허용 금지.
- [ ] 소유 크루 승계/해산, 파티 취소, 채팅 익명화·보관, GPS 삭제, 원장 보존을 포함한 탈퇴 설계.
- [ ] 토큰 회전·삭제·만료 및 이전 세션 무효화. 새 비밀 서버 키는 APK 밖에 보관.

완료 조건: 재설치/기기 교체 후 동일 계정과 기록을 복구하며, 삭제 요청은 FK 오류 없이 처리한다.
보존한 데이터와 삭제한 데이터를 사용자에게 정확히 설명한다.

## 3. GPS·기록 품질 강화와 실기기 기준 측정

대상: A05/A06/A07.

- [ ] 좌표 freshness를 자동 정지/재개 전에도 검사. pause/recovery/low-accuracy GPX 연결 테스트.
- [ ] 1시간/3시간 경로에서 메모리·CPU·DB 쓰기·지도 재구성 측정 후 최적화.
- [ ] 실제 기준 5km 야외 코스, 화면 끔, 앱 백그라운드, 네트워크 단절, 권한 해제, 프로세스 종료·재부팅 복구.
- [ ] 기기 모델/OS/절전 설정/기준 거리/실측 거리/소모 배터리/발열/누락점/복구 결과 기록.

완료 조건: 기존 목표인 5km 오차 3% 이내를 실측하며, 일시정지 이동은 거리/보상에 연결되지 않는다.
수집 완료점은 복구되고 관측하지 않은 구간을 만든 것처럼 표시하지 않는다.
배터리·발열 기준은 첫 측정 자료를 바탕으로 수치화한다.

## 4. 2대 음성·DJ 음악 검증

대상: A08. GPS 기록과 동시에 실행한다.

- [ ] LiveKit·bridge 테스트 환경 구성, TLS/WSS, 동일한 bridge secret, readiness와 실제 연결 상태 구분.
- [ ] 음성0/음악0 각각 해당 트랙만 무음인지 2대에서 확인.
- [ ] 파일 EOF, 캡처 취소, 연결 단절, 권한 철회, 역할 강등, 차단, 탈퇴 시 자원·참가자·lease 정리.
- [ ] 스피커/유선/블루투스별 지연·통화 모드·발열·배터리 기록.
- [ ] 6개 외부 음악 앱의 버전/콘텐츠/출력 장치별 캡처 결과를 분리.

완료 조건: 방당 음악 1개, 강등/취소 뒤 음악 차단, 기존 음성 참가자 권한 철회가 확인된다.
외부 앱이 캡처를 거부하는 경우 사용자가 결과를 알 수 있으며 GPS 기록은 계속된다.

## 5. Supabase adapter와 실행형 DB 검증

대상: A09/A10. 운영 DB 대신 비운영 테스트 프로젝트/로컬 DB에서 먼저 수행한다.

- [ ] 실제 PostgreSQL에 migration 적용 및 현재 pgTAP 23개 실행. 구문 파싱을 RLS 통과로 대체하지 않기.
- [ ] anonymous/타인/일반회원/DJ/크루장/service_role별 권한 테스트.
- [ ] 앱 pilot presence와 SQL crew/party scope 차이 해결. 외부 노출 대상은 명시 동의한 범위로 한정.
- [ ] tracks 순번·segment·거리 재계산·finalize·구매·정원 트랜잭션 adapter 구현.
- [ ] 같은 마지막 자리 동시 신청, 같은 기록 중복 finalize, 일일 상한·구매 경쟁, 삭제 중 요청 검증.
- [ ] 현재 SQLite 데이터 이관 dry-run, 건수·소유권·보상 검증, 전환/복구 절차.

완료 조건: Android→HTTPS API→PostgreSQL→응답 전체 흐름을 재검증하고,
타인의 GPS·원장·채팅 접근 거절과 동시 요청 일관성을 실행 증거로 확인한다.

## 6. 소규모 외부 HTTPS 운영과 관측

대상: A11/A12. 1~5단계 완료 후 성인 지인 5~20명으로 시작한다.

- [ ] API 상시 실행, SQLite 파일럿 유지 시 볼륨·단일 writer 정책, cloud 전환 시 연결/트랜잭션 설정.
- [ ] TLS·프록시·허용 origin·본문/요청 상한·rate limit·health·오류/비용 알림.
- [ ] GPS·토큰·초대 코드를 제외한 구조화 로그. 위치 보존/삭제 주기와 TTL 정리 작업.
- [ ] 백업을 실제 복구해 계정/기록/원장 정합성 확인. 배포 rollback 훈련.
- [ ] 폴링 부하·긴 기록 조회·채팅 페이지·오프라인 오류 표시 측정.
- [ ] 위치 해제/종료/탈퇴 뒤 45초 이내 미노출, 차단·신고 UI와 운영 대응 절차.

완료 조건: 5~20명 동시 실행에서 기록 손실·초과 정원·중복 보상·권한 누출이 없고,
운영자가 장애 감지·위치 제거·복구를 수행할 수 있다.

## 7. 배포·제품 검증

- [ ] 서명 키 백업/같은 인증서 업데이트, release AAB/ABI·다운로드 크기·시작 시간 점검.
- [ ] 개인정보 처리방침·계정 삭제 안내·위치/오디오 동의·스토어 데이터 공개 항목 작성.
- [ ] 핵심 사용성: 기록 시작 성공률, 완료 후 복구, 파티 재참여, DJ 사용 시 유지율 측정.
- [ ] 푸시는 파일럿에서 일정 알림 필요가 확인되면 추가.
- [ ] 유료 꾸미기/결제·콘텐츠 권리·미성년자 확장은 별도 제품/정책 결정 후 착수.

완료 조건: 실제 사용자 검증 결과와 남은 제한을 포함한 출시 판단을 기록한다.
현재 개발 APK와 이번 CI 추가를 대중 서비스 출시 완료로 취급하지 않는다.
